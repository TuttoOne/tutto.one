Writing your skill file

The most valuable thing you build with us is the rules. The script that runs them can be rewritten in an afternoon, but the rules are what a senior person in your role knows, written down so it stops living in one head.

Takes about 5 minutes to readThen the evals guide, to prove the rules work

What a skill file is

A plain Markdown file. There's no special syntax and no code, just prose and bullet points, the way you'd write a briefing note or a checklist for a new hire.

It opens with a short header so anyone who reads it knows whose rules these are:

Role: Due Diligence Analyst
Use case: target company review memos
Data types: company filings, auditor reports, news clippings
Last updated: 2026-06-04

Then the rules.

What goes in the rules

Rules are the things a senior person does automatically that a junior wouldn't know yet. It's the knowledge that isn't in any manual.

Good rules are specific and you can test them. "Be thorough" doesn't tell anyone what to do. "Flag any supplier whose payment terms exceed 60 days" does.

Start by asking yourself what would make you send a piece of work back. Those are your rules. Then ask what would make a client call to complain, and add those too.

Here's a set for a BD analyst writing prospect research memos:

Rules:
- Lead with the decision. The first sentence is the recommendation.
- Cite a source for every factual claim: (Source: [filename], p.[page]).
- Flag any company that has changed leadership in the last 18 months.
- Note if the company's stated headcount differs from LinkedIn estimates by more than 20%.
- Use the client's language for their industry, e.g. "rig" for offshore, never "vessel".
- Sections: Executive Summary, Company Overview, Key Risks, Recommended Next Steps.
- Keep the Executive Summary to 3 sentences.

How to write your own

Open Claude Code and start a conversation. Tell it your role, your use case and the task you want it to take on. Then ask:

"Help me write the rules for [your task]. I want the kind of rules a senior [your role] follows that a new junior wouldn't know yet."

It drafts something. Read it back and correct it. Take out anything generic and add the things from your field that only you would know. The version you end up with is yours.

Then test it: could a competent person in your role read this file and produce work you'd be happy to sign off? If they couldn't, keep adding rules until they could.

The file stays on disk

A common mistake is to write the skill file as a prompt, something to paste into a chat window and lose.

It lives in your project folder, Claude reads it every time it does the job and Git keeps every version. When your rules change, and they will, you update the file and the next run picks up the new rules. Nobody has to remember to paste anything.

It's also for the next person in your role, or for you in six months when you've forgotten why you wrote rule 7.
