Claude in Amazon Bedrock — teaching notes

Side-by-side notes for 10-praxis-claude-in-amazon-bedrock.html (11 slides). This is the developer course delivered on AWS Bedrock: the same SDK and the same ideas as the direct API course, but the door is AWS. The whole course has one Praxis translation that earns the room: where the model runs is the data-residency story. Bedrock is the "ceiling" option — Claude runs inside your own AWS tenancy and your data stays in your environment. Teach the mechanics for the technical people, but always come back to that for the regulated room. Written from the deck and 10-claude-in-amazon-bedrock-lessons.txt, against the Praxis teaching library. Method: teaching-notes-method.md.

How to use these notes
  • Guidance, not a script. Teach the person, not the slides. This deck leans technical; most rooms will have one or two people who could write the code and several who will only ever commission it. Pitch to both: the mechanic for the builder, the so what for the buyer.
  • Every teaching slide has a Pause, then ask block. Put the question, then stop. Don't fill the silence. If they freeze: "Take your time, type anything when you're ready, including 'I don't know'." Then wait again.
  • By background gives a line per archetype (tutor/scenarios.md). Reach for the one in the room and ignore the rest. A palette, not a checklist. Several slides here are pure AWS plumbing (IAM, model ids, SDK calls) that does not vary by domain — there you get one shared example and a note saying so, per the method. Don't manufacture nine.
  • Hold the voice (train-the-trainer.md Part 4): no "great question", no emoji, one term — Claude Code. Underclaim. Cost is "about twenty dollars a month" and stop. Don't read code aloud.
  • The recurring Bedrock thread: when someone asks "but where does our data go?", this is the course where the honest answer is into your own AWS account, not out to a vendor. That is the floor-and-ceiling conversation (objections.md — IT/compliance), and Bedrock is the ceiling. Keep it in your pocket for every slide.

Build with Claude, delivered on AWS Bedrock

The idea

Set the frame: this is the full Claude developer course, eight chapters, one screen each. The intelligence and the SDK are identical to the direct API; the only change is the door — you come in through AWS. For most rooms that distinction is the reason they're here.

Say it like this

"Eight chapters, one screen each. Everything in this course you could also do against Anthropic's API directly. What changes on Bedrock is one thing: the model runs inside your AWS account, on your terms, in your region. If that sentence matters to your compliance team, this is the right course. If it doesn't, the API course teaches the same craft."

Open with

If you know the room is regulated — a bank, a firm, a healthcare operator — name it now: "The reason we're on Bedrock and not the plain API is the one your IT team cares about, and we'll come back to it on every slide." That promise is the hook.

Chapter 1 · Talk to Claude

A conversation is a list of messages

The idea

A request is a message list plus a system prompt plus a few dials (temperature, max tokens, streaming). Claude appends its reply; you append it back and send again — that's a multi-turn conversation. On Bedrock the shape is unchanged; only the door differs: AWS credentials and a region instead of an Anthropic key, and a Bedrock model id.

Say it like this

"A conversation is just a growing list of messages. You send the whole list each turn, Claude adds its reply, you add the next thing and send it all back. The system prompt sets the role and the rules. Three dials shape the output. And the Bedrock difference is only the door, not the shape: AWS credentials and a region instead of an Anthropic key. Everything past this slide is the same SDK." (Pairs with 01 Lesson 1 — thinking partner, not a one-shot chatbot: the back-and-forth is the point.)

Pause, then ask
  • "Whose AWS account would this run in — yours, or a client's? Who owns the region it lives in?"
  • "What's the work you'd want to do back-and-forth with it, rather than one question, one answer?"

(wait)

Chapter 2 · Make it reliable

Measure the prompt, don't eyeball it

The idea

"Looks good" doesn't scale. Build a test set, run the prompt across every case, grade the answers (Claude grades the open-ended ones; code checks the exact ones), get a score. Then you can prove a change is an improvement instead of guessing. Claude can write the test set for you.

Say it like this

"The instinct is to read one answer, decide it looks fine, and ship. That doesn't scale and it doesn't survive a regulator asking 'how do you know it's right?'. An eval is the answer: a set of test cases, the prompt run across all of them, a grade on each, and a single score you can beat. Change the prompt, run it again, watch the number move. Claude can even generate the test set for you." (This is the rigour behind the Praxis 80/20 promise — patterns.md, the 80/20 expectation: the eval is how you measure the 90%.)

Pause, then ask
  • "How do you know today that one of your reports or outputs is right? What would you point an auditor at?"
  • "What does 'good enough to ship' look like for your work — specifically enough that a score could measure it?"

(wait)

By background (the test set is their own worked cases)
Investigator
twenty past background reports with known-correct findings — does the prompt reproduce them, every source cited?
Analyst
known vendor comparisons where you already know the right table — grade whether the "no data" cells are honest.
Designer
a set of briefs with the asset manifest you'd hand-built — did it miss any variant?
Knowledge worker
fifty invoices you've already extracted by hand — does the score say the CSV matches?
Reporter
past weeks' updates with the briefing you actually sent — does it land the same five sections?
Content
past posts scored for on-voice — does the draft pass the house-voice grade?
Form-filler
receipts with the correct allocation known — does every line land in the right section?
Outreach
customer files with proposals you approved — does it reproduce them without inventing numbers?
Exec
past board cycles where you know what mattered — does the brief surface the same decisions?
Watch for

Evals are the unglamorous slide people skip, and the one that separates a toy from something a regulated firm will sign off. For the bank and the firm in the room, dwell here: this is the audit trail. Tie it to grading rigour, not to features.

Chapter 3 · Make it reliable

Clarity first, examples last

The idea

Reach for prompt techniques in order of cost: be clear and direct, then be specific, then add structure (XML tags to separate the parts), then — last and most expensive — show examples. Most prompts are fixed by being clearer, not cleverer. Examples are the strongest lever and the priciest in tokens, so spend the cheaper rungs first.

Say it like this

"There's an order to this. First, just be clear and direct — say exactly what you want. Then be specific — spell out the detail. Then add structure, tags that separate the instruction from the data. And only then, if you still need it, show it an example. Examples are the most powerful move and the most expensive, so you reach for them once the cheaper rungs are spent. Most disappointing answers are fixed two rungs down, by being clearer." (Pairs with 01 Lesson 2 — set the stage, define the task, specify the rules. This slide is that brief, ordered by cost. And framings.md — brief like a junior: spell it out, the mistake is being too economical with words.)

Pause, then ask
  • "Think of the last time AI gave you something useless. Was the prompt actually clear, or did you assume it knew something only you knew?"
  • "What's the one example you could show it that would say more than a paragraph of instruction?"

(wait)

By background (the rung that fixes their most common failure)
Investigator
be specific — "cite every source, classify primary vs reported, never infer conduct"; the rule set is the prompt.
Analyst
structure — tag the columns and the basis so the table comes back like-for-like.
Designer
examples — one finished asset beats three sentences describing the look.
Knowledge worker
be specific — the CSV schema and "leave blanks blank".
Reporter
be clear and direct — who reads this and the five sections it must have.
Content
examples — paste two past posts; the voice is in the sample, not the adjectives.
Form-filler
structure — tag each receipt and each template section so allocation is unambiguous.
Outreach
be specific — the customer file is the source, no invented numbers.
Exec
be clear and direct — "one page, facts not editorial, every decision has an owner".
Watch for

People reach straight for examples (the expensive rung) because it feels like the "pro" move, and skip clarity. Steer them down: try clear-and-direct first, measure with the eval from the last slide, only climb if the score needs it.

Chapter 4 · Give it reach

Claude asks, your code answers

The centrepiece. If they take one thing away from the whole course, it's this.

The idea

Tool use is the pivot. Claude can't run your code, so it asks — in structured JSON, naming a tool and its inputs. Your code runs the function and hands the result back as a message. Claude reads it and continues, looping until done. A JSON schema defines each tool. Everything else in the course — multiple tools, batching, structured extraction, agents — is this one exchange repeated.

Say it like this

"This is the hinge of the whole course. Claude can't reach into your systems and run things itself. So instead it asks: it says, in structured form, 'call this tool with these inputs'. Your code runs it, hands back the result, and Claude carries on. That's it. Multiple tools, batches, extracting clean data, full agents — all of it is this one exchange, looped. Master this and the rest is repetition." (This is the API-level version of the connectors idea from 01 Lesson 8 — bringing your tools into the conversation — except here you define the tool and you hold the keys.)

Pause, then ask
  • "What's the system or database Claude would need to reach into to be genuinely useful to you — and who controls access to it?"
  • "Where would you want it to look something up or take an action, rather than just draft text?"

(wait)

By background (the tool they'd wire up)
Investigator
a tool that queries the case-management system or a sanctions API — running inside the firm's own account, so the lookup never leaves the tenancy.
Analyst
a tool that pulls the figure from the warehouse, so the number is sourced, not generated.
Designer
a tool that reads the retailer spec sheet and returns exact dimensions.
Knowledge worker
a tool that writes the validated row to the accounting system.
Reporter
a tool that fetches each team member's latest status from the tracker.
Content
a tool that checks a claim against the CMS before it goes in the post.
Form-filler
a tool that looks up the current threshold or allowance before allocating.
Outreach
a tool that reads the CRM record for the customer being written to.
Exec
a tool that pulls the live KPI rather than a number that might be stale or invented.
Watch for

The "what if it gets it wrong" fear peaks here, because now it's doing things, not just drafting. Answer it the Praxis way: the tool returns real data, the code enforces the rules, Claude doesn't get to decide the rules. (objections.md — hallucinate / make stuff up.) And on Bedrock, add: the tool runs inside your AWS account, so even the reaching-out happens in your environment.

Chapter 5 · Give it reach

Retrieve the right context, then answer

The idea

Claude only knows what's in the prompt. RAG (retrieval-augmented generation) finds the few relevant passages from your own documents and puts them there before Claude answers. Index once (chunk, embed, store), then per query run two searches — semantic for meaning, BM25 for exact terms — rerank to the best, drop the top passages into the prompt, and answer grounded in your material. Contextual retrieval adds a line of context to each chunk so it survives being torn from its document.

Say it like this

"Claude knows what's in the prompt and nothing else. RAG is how you feed it your own documents without pasting all of them in. You index them once, then for each question you run two searches — one for meaning, one for the exact words — keep the best handful, and put just those passages in front of Claude. The answer is grounded in your material, with the source attached." (This is the under-the-hood version of the "folder is the memory" idea from framings.md — except at API scale, over thousands of documents.)

Pause, then ask
  • "What's the body of documents you'd want it to answer from — and where does that corpus physically live today?"
  • "Where do you currently open ten files to answer one question?"

(wait)

By background (the corpus they'd index — note where it must stay)
Investigator
the firm's precedent library and past reports — indexed inside the firm's account, never copied to a vendor index.
Analyst
every past vendor submission, searchable so the comparison cites real prior answers.
Designer
the brand guideline library and past campaign specs.
Knowledge worker
the archive of supplier terms and known quirks.
Reporter
the back-run of past briefings, so context carries week to week.
Content
the full back catalogue, retrieved for voice and to avoid repeating a topic.
Form-filler
the rulebook and category definitions, retrieved per receipt.
Outreach
the knowledge base of market claims, cited per proposal.
Exec
the retainer book and board-pack history, queried for "what changed".
Watch for

RAG is where the data-residency point gets sharpest: a hosted RAG vendor means your whole corpus sits in someone else's index. The Bedrock answer is that the embeddings and the store can live inside your own AWS account. For the regulated room, this is the slide where the floor-and-ceiling really pays off. Chapter 6 · Give it reach

Beyond text

The idea

The same message API carries more than words. Claude can think longer before answering, read images and PDFs (vision), cite its sources, and — the cost lever — cache a stable prefix. Put the unchanging parts first (system prompt, long documents, tool definitions); on repeat calls that prefix is read from cache instead of reprocessed, so calls get cheaper and faster.

Say it like this

"Four capabilities on the same API. It can think before it answers, for hard problems. It can read images and PDFs, not just text. It can cite its sources, so the answer points back at the document. And it can cache — this is the cost lever. The trick is to put the unchanging parts of your prompt first: the system prompt, the long reference document, the tool definitions. On every repeat call, that stable prefix is read from cache instead of reprocessed. Same documents, many calls, far cheaper." (Citations answer the hallucination fear from objections.md directly; vision answers the "but my files are PDFs and scans" worry from objections.md — Word/Excel/PDF.)

Pause, then ask
  • "How much of what you'd send it is the same every time — the same rulebook, the same long reference doc?"
  • "Where would 'the answer cites the exact page' change whether you'd trust it?"

(wait)

By background (the cacheable prefix and the feature that earns its place)
Investigator
cache the screening checklist and house rules; citations make every claim traceable to a filing.
Analyst
cache the column definitions; citations tie each cell to a submission.
Designer
vision — it reads the reference image and the spec sheet directly.
Knowledge worker
vision reads scanned invoices; cache the schema across the whole batch.
Reporter
cache the format and roster; thinking helps it judge what matters.
Content
cache the house-voice guide; vision reads a reference layout.
Form-filler
vision reads scanned receipts; cache the template and category definitions.
Outreach

Watch for

Caching is the slide that answers the cost objection at scale, but don't let it pull you into a big-number conversation. Keep the tutor line: building uses model calls, running is nearly free, and caching makes the building cheaper too — "about twenty dollars a month" for most. Chapter 7 · Build systems

One protocol: tools, resources, prompts

The idea

MCP is one standard for wiring a capability once so any client can use it. A server offers three things — tools (actions Claude can call), resources (data it can read), prompts (ready-made templates). Build it once and it drops into any MCP client — Claude Code, your own app — with no bespoke glue per integration. Tools do, resources inform, prompts reuse; the protocol is the contract between them.

Say it like this

"MCP is the standard that stops you rebuilding the same integration for every tool. You wire a capability once as a server — it exposes actions, data, and reusable templates — and any client that speaks the protocol can use it unchanged. Build it once, use it everywhere. It's the same idea as connectors from the introductory course, but here you're building the connector, not just consuming one." (In 01 Lesson 8 MCP was "USB-C for AI", the one standard behind connectors; this is that standard from the builder's side.)

Pause, then ask
  • "What's the one capability you'd want every AI tool in your firm to share — and build only once?"
  • "Where do you re-explain the same integration or the same process to every new tool you adopt?"

(wait)

Chapter 8 · Build systems

An agent is the loop plus tools plus autonomy

The idea

Everything earlier composes here. An agent is prompting plus tool use plus retrieval plus MCP, running its own loop — act, observe, decide, repeat until the job is done. Good agents share three qualities: clear tools, a way to verify their own work, and bounded autonomy. Claude Code is the reference agent. Computer Use is the far end — Claude driving a screen when there's no API to call.

Say it like this

"An agent is everything we've built, composed. Prompting, tools, retrieval, MCP — wired into a loop that acts, looks at the result, decides the next move, and repeats until it's done. The good ones have clear tools, a way to check their own work, and bounded autonomy — they don't run forever. Claude Code is the reference example, the agent in your codebase. And at the far end is Computer Use, where it drives a screen like a person, for the times there's no API to call." (The autonomy fear from 05 Lesson 2 lives here: give the controls before the capability — confirm-each-step first, auto-mode once trusted, you always check the end. objections.md — permission/auto.)

Pause, then ask
  • "What's a multi-step job — fetch, decide, act, repeat — that you'd let run on its own once you trusted it?"
  • "What would have to be true before you'd hand a whole process over, not just one step?"

(wait — the second question surfaces the autonomy fear; let it sit.)

By background (the agent loop, and the bound they'd set)

an agent that runs the full screening pass per subject — bounded to draft, never to file; you sign off.
Analyst
an agent that pulls, tabulates and flags every submission — you adjudicate the comparability.
Designer
an agent that generates the full variant set from a brief — you curate.
Knowledge worker
an agent that processes the whole inbox folder — flagged rows held for review.
Reporter
an agent that consolidates every update into the weekly briefing — you decide the narrative.
Content
an agent that drafts against the back catalogue — you own voice and publish.
Form-filler
an agent that allocates a full filing period — totals must reconcile before it stops.
Outreach
an agent that drafts one proposal per customer — none sent without your approval.

an agent that assembles the board brief — facts only, you carry the judgement.
Watch for

This is where excitement outruns trust. Hold the line that the human stays in the loop by design, not as a temporary limit (05 Lesson 12 — discernment is not a step you automate away). On Bedrock, add the one thing the audit committee wants: the whole agent, loop and tools and data, runs inside your own AWS account.
