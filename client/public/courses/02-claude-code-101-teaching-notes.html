Claude Code 101 — teaching notes

Side-by-side notes for 02-praxis-claude-code-101.html (15 slides). This is the more technical course: the agentic loop, install, Explore → Plan → Code → Commit, context and CLAUDE.md, subagents, skills, MCP, hooks. Course 01 deliberately bridges the nine non-technical archetypes into this one, so keep the framing on "what this means for your world", not the engineering. The deck is what the room looks at; this is what you say, where you stop, and how each idea lands for the person in front of you. Written from the deck and 02-claude-code-101-lessons.txt, against the Praxis teaching library. Method: teaching-notes-method.md.

How to use these notes
  • These are guidance, not a script. Teach the person, not the slides.
  • Each teaching slide has a Pause, then ask block. Put the question, then stop. Do not fill the silence. If they freeze, one line: "Take your time, type anything when you're ready, including 'I don't know'." Then wait again.
  • By background gives you a line per archetype (from tutor/scenarios.md). Reach for the one that matches whoever is in the room and ignore the rest. They are a palette, not a checklist to read out.
  • This course names commands (/compact, /init, /agents) and a file (CLAUDE.md). Say them; do not read code aloud (framings.md — voice). The point of every command is the outcome, not the keystroke.
  • Hold the voice (train-the-trainer.md Part 4): no "great question", no emoji, one term only — Claude Code. Underclaim. Cost is "about twenty dollars a month" and stop.
  • Run the intake first (train-the-trainer.md) so you know which background you're teaching to. If the room hasn't done course 01, plant the bridge: this is the durable, on-your-disk version of everything Claude does in the browser.

Title

What Claude Code actually is, and how to work with it

The idea

Set the frame: twelve ideas, one per screen. You show each one working, then hand it back to them. No lecturing. The subject of the session is one change: Claude stops answering and starts doing the work itself.

Say it like this

"There are twelve ideas in this course, one per screen. They all point at one change. Up to now, Claude has given you text and you did the rest — you copied it out, used it, fixed it. Claude Code does the work itself, in your own files, on your own computer. For each idea I'll show you it working, then stop and ask where it fits in your week. You don't need to remember it all today."

Open with

The task they named in intake: the recurring grind that lives across many files. Promise you'll come back to it when you reach the workflow slide, because that is the task they'll set up once and reuse.

Spine

The whole course on one screen

The idea

Four moves: understand the tool, get it running, learn the one workflow, then customise it to your work. Show the plan so nobody feels lost once the terms start coming.

Say it like this

"This is the plan for the session, in four parts. First, what Claude Code is and how it works. Then, getting it running on your machine. Then, the one workflow to learn: explore, plan, code, commit. And last, how to set it up for your own work. If a term comes up and you don't know where it belongs, we come back to this screen."

Cue

Don't teach the spine, just orient. The centrepiece is slide 7, Explore → Plan → Code → Commit; everything else serves it. Twenty seconds, then move.

Lesson 1 · Foundation

Chat answers. An agent acts.

The idea

A chat hands text back and waits; you carry it across. An agent reaches into your files, terminal and codebase and does the work itself, then decides what to do next.

Say it like this

"In a chat, you ask a question and get text back, and then the rest is on you: you copy the answer out, use it somewhere, and paste back whatever went wrong. An agent removes that carrying. It reads your files, edits them, runs the commands, checks the result, and keeps going until the job is done. It's the same Claude you know from the browser. The difference is that it can act on your computer instead of only answering." (Pairs with framings.md — the folder is the memory: the work moves out of a chat you lose and into a place that persists.)

Pause, then ask
  • "Where in your week are you the courier — copying something out of one tool, doing a step, pasting the result back in?"
  • "What would change if that middle step just happened?"

(wait)

By background
Investigator
it opens the case file itself instead of you pasting documents in one by one.
Analyst
it reads every vendor response in the folder, not the one you hand it.
Designer
it works across the whole brief set, not a single brief you upload.
Knowledge worker
it processes the inbox folder in place, no file-by-file copy.
Reporter
it pulls every team update from where they live and writes the briefing.
Content
it reads the back catalogue on disk to match your voice, unprompted each time.
Form-filler
it allocates a whole folder of receipts, not one you paste in.
Outreach
it reads every customer file and drafts a proposal per file.
Exec
it assembles the board inputs from the folder instead of you collating them.
Watch for

"Is my data safe once it's in my files?" surfaces the moment they picture it acting, not just answering. Don't wave it away. The files exist with or without Claude; it sits dormant until you summon it, and it sees only that folder. (objections.md — "where is the AI" / IT-compliance; full treatment on the MCP slide.)

Lesson 2 · Foundation

The agentic loop

The idea

Everything sits on one cycle: prompt, gather the context it needs, act, verify — and loop back until the result holds up. You can add context, interrupt, or steer at any point.

Say it like this

"Underneath, it runs a cycle. You give it an instruction. It gathers the context it needs. Then it acts: it edits files, runs commands, searches. Then it checks its own work, and if the result isn't right, it tries again. When it's done, it stops and waits for you. You can step in at any point along the way — add a file, correct something, or send it in a different direction." (Four parts make the loop run: the loop itself, a managed memory, the tools it can call, and the permissions you control — that combination is what a chat doesn't have.)

Pause, then ask
  • "When you hand a task to a capable colleague, what do you trust them to figure out without asking you every step?"
  • "Where would you want to watch closely, and where would you happily let it run?"

(wait)

By background
Investigator
it cross-checks names across files and reruns the screen if one comes back thin.
Analyst
it spots a blank cell, goes back to the source, confirms there's no data.
Designer
it lists assets, notices a missing spec, flags it rather than guessing.
Knowledge worker
it reads an odd invoice, can't parse a field, routes it to review.
Reporter
it gathers updates, sees a teammate didn't submit, notes "no update" and carries on.
Content
it drafts, checks against the house voice, rewrites the line that drifted.
Form-filler
it allocates a receipt, hits an ambiguous one, files it to "to allocate".
Outreach
it drafts a proposal, finds a number isn't in the file, leaves it out.
Exec
it builds the brief, finds a renewal with no logged conversation, surfaces it.
Watch for

"What if it does something I don't want?" The answer is the next slide: permissions. Don't sell autonomy before you've shown the brakes. (objections.md — permission / "scary to let it".)

Lesson 3 · Setup

Five places it runs

The idea

Same agent, five front doors — terminal, VS Code, JetBrains, Desktop, web. Wherever you run it, it can reach that folder and everything beneath it. Sign in with a Claude account or an API key.

Say it like this

"You can run Claude Code in five places: in the terminal, inside an editor like VS Code or JetBrains, in the desktop app, and on the web. The terminal gets new features first. The desktop app is the easiest place to start, because it runs in the background while you do other things. The rule that matters is the same everywhere: you start it in a folder, and it can see that folder and everything inside it, and nothing above it." (framings.md — demystifying the terminal: it's just the bare-metal way to talk to your computer, the same cd you typed to launch a game in the nineties.)

Pause, then ask
  • "Which surface would feel least alien to you to start in?"
  • "Where do the files for that recurring task actually sit on your machine?"

(wait)

By background
Investigator
Desktop or VS Code, pointed at the case-file folder, after the IT conversation.
Analyst
VS Code on the folder of vendor responses; terminal once it's routine.
Designer
Desktop alongside the design tools, on the brief folder.
Knowledge worker
Desktop, running in the background over the inbox folder.
Reporter
wherever the updates land; Desktop is the gentlest start.
Content
VS Code or Desktop on the back-catalogue folder.
Form-filler
Desktop on the receipts folder, watching it work the first few times.
Outreach
Desktop or VS Code on the customer folder; web if the CRM exports to GitHub.
Exec
Desktop, pointed at the board-inputs folder, running while they do other work.

"I'm not technical, the terminal is scary." Default to Desktop or VS Code, not the terminal. Lesson 4 · Setup

One key sets how much you watch

The idea

Shift + Tab cycles how hands-on you are: Approval (asks before every edit or command), Auto-accept (edits flow, commands still ask), Plan mode (read-only — researches and writes a plan before a single file changes). No right answer, only your comfort.

Say it like this

"One key, Shift + Tab, sets how closely you watch it work. There are three settings. Approval mode asks you before every change; that's where you start, because watching it ask is how you build trust. Auto-accept lets the edits happen without asking, for when you've seen the pattern enough times. And Plan mode is read-only: it studies the files, asks its questions, and gives you a plan. Nothing changes until you approve the plan." (objections.md — permission: confirm-each-step first, switch to auto when the pattern is familiar, you always check the end.)

Pause, then ask
  • "On a task that matters, would you rather approve each step, or see the finished result and check it?"
  • "What's the kind of work where you'd want it to plan first and show you, before doing anything?"

(wait)

By background
Investigator
Plan mode, then Approval — high stakes, you watch every step at first.
Analyst
Approval while the comparison logic is new; the table is auditable either way.
Designer
Auto-accept once the manifest format is set — low risk, fast iteration.
Knowledge worker
Approval the first month, Auto-accept once the extraction is trusted.
Reporter
Auto-accept — the briefing is reviewable before it goes out anyway.
Content
Auto-accept for drafting; you're editing the output regardless.
Form-filler
Approval — you want to see each allocation until the rules are proven.
Outreach
Approval while wording is sensitive, Auto-accept for batch once it's right.
Exec
Plan mode for anything board-facing; see the plan before a number moves.
Watch for

People hear "auto" and picture losing control. Frame it the other way: you always check the end, and Plan mode means nothing changes until you approve a plan. Trust is built on Approval first. (objections.md — permission / "what if it does something I don't want".)

Lesson 5 · The method

Explore → Plan → Code → Commit

The centrepiece. If they take one thing away, it's this.

The idea

Most people jump straight to "write the code" and course-correct forever. The workflow that saves the rework: Explore (read, gather context), Plan (something you can measure against), Code (the back-and-forth to the result), Commit (review, then push). Plan mode does the first two — the cheapest place to course-correct.

Say it like this

"If you keep one thing from today, keep this workflow. It has four steps. First, explore: it reads what's already there. Second, plan: it writes out what it intends to do, and you correct that plan. This is the cheap place to catch a mistake — changing a plan takes a minute, changing finished work takes an afternoon. Third, it does the work, back and forth with you. Fourth, you review the result and commit it. Most people skip straight to the third step, and then spend their time correcting the output." (framings.md — the 80/20 expectation, set it here, before any live run: "You'll get ninety percent of the way; you finish the last ten — and even eighty percent is an enormous cut.")

Pause, then ask
  • "Think of a job you've handed off that came back wrong. Would seeing the plan first have caught it?"
  • "Take that task you named in intake — what would 'done right' have to include for you to trust it?"

(wait — making "correct" explicit is the lesson.)

By background (Explore and Plan, in their words)
Investigator
explore the case file, plan the report's eight sections, then write.
Analyst
explore the responses, plan the columns and the "no data" rule, then build.
Designer
explore the briefs, plan the full asset list, then generate the manifest.
Knowledge worker
explore the invoice formats, plan the CSV schema, then extract.
Reporter
explore the updates, plan the five sections, then write the briefing.
Content
explore the back catalogue, plan the post's argument, then draft.
Form-filler
explore the receipts and template, plan the allocation rules, then fill.
Outreach
explore the customer files, plan the proposal sections, then draft each one.
Exec
explore the inputs, plan the four-part brief, then write the page.
Watch for

They'll want to skip to the result and be disappointed. The plan is the work; correcting a plan costs minutes, correcting finished output costs an afternoon. Set 80/20 before you run anything live. (patterns.md — the 80/20 expectation. The caption's quick tip — if it keeps hitting the same wall, tell it to save the fix to CLAUDE.md — previews slide 10.)

Lesson 6 · The method

Context is working memory, it fills up

The idea

Every file read, command run and message sent takes space in the context window. Three commands keep it usable: /compact (summarise, keep the thread), /clear (wipe it, new feature), /context (see what's filling it). Near the limit it auto-compacts.

Say it like this

"Claude has a working memory, and it fills up. Every file it reads and every command it runs takes up space in it. Three commands manage that space. /compact summarises the conversation so far — you keep the thread of the task but free up room, so use it in the middle of a long job. /clear empties the memory completely, for when you start something unrelated. /context shows you what's taking up the space. Anything you want it to keep beyond the session goes in a file, and that file is the next slide." (framings.md — context window: the browser chat forgets the beginning once it runs long; here the memory is bounded by your disk, not a chat.)

Pause, then ask
  • "When you've used a chatbot on a long task, have you felt it lose track of what you said earlier?"
  • "Which of your tasks are one clean job, and which sprawl across many steps?"

(wait)

By background (when to /clear vs /compact)
Investigator
/clear between unrelated subjects; /compact mid-report on one matter.
Analyst
/clear between vendor reviews; /compact while still building one table.
Designer
/clear between campaigns; /compact mid-manifest on one campaign.
Knowledge worker
/clear between months; /compact part-way through a big batch.
Reporter
/clear each new week; /compact while still assembling this week's.
Content
/clear between posts; /compact mid-draft on one piece.
Form-filler
/clear between filing periods; /compact part-way through one period.
Outreach
/clear between segments; /compact mid-batch on one segment.
Exec
/clear between board cycles; /compact while still building one brief.
Watch for

"Does it forget like ChatGPT?" Yes, a long chat does — that's exactly why the durable rules live in a file (slide 10), not in the conversation. Tip worth saying: a vague prompt costs more context, not less, because it has to go exploring to fill the gap. (objections.md — browser / why not ChatGPT.)

Lesson 7 · The method

Fresh eyes before you push

The idea

The agent that wrote the work carries its own bias. A subagent reviews it cold, in its own context, read-only. /commit-push-pr does commit, push and PR in one step; claude --from-pr <n> resumes the session later.

Say it like this

"The Claude that did the work is not a good judge of it, for the same reason you're not a good judge of your own writing: it made the choices, so it defends them. So before the work goes out, a second Claude reads it with no memory of how it was made. It can point at problems, but it can't change anything. Then one command saves the work and posts it for review. And you can come back to that piece of work later and carry on from where you stopped." (Adapt to their world: this is the same instinct as a colleague checking your work before it goes to the client.)

Pause, then ask
  • "Who checks your work today before it goes out, and what do they catch that you miss?"
  • "Where would a second cold read save you from sending something with a hole in it?"

(wait)

By background (what the cold review catches)
Investigator
an unsourced claim, or an inferred associate the file didn't support.
Analyst
a cell guessed instead of marked "no data", or a mismatched basis.
Designer
a variant missing from the manifest, or a spec it filled in instead of flagging.
Knowledge worker
an invented VAT number, or a credit note with the sign dropped.
Reporter
a missing teammate quietly omitted instead of marked "no update".
Content
a line that drifted off the house voice, or a banned rhetorical question.
Form-filler
a receipt allocated to two sections, or totals that don't reconcile.
Outreach
a number that isn't in the customer file, or a question in the subject line.
Exec
a risk editorialised ("at risk") instead of stated as fact, or a projection.
Watch for

This is abstract until you tie it to a real handoff they trust. The point isn't git mechanics; it's that a second, unbiased pass catches what the author can't. Keep the reviewer read-only — it flags, it doesn't fix. (Mirror of course 01 slide 5: the cited report is how you catch "confident but wrong".)

Lesson 8 · Customise

CLAUDE.md, memory that survives the session

The idea

Without it, Claude re-learns your project every time. With it, it starts already onboarded. A plain file at the project root, read every session, appended to every prompt. Two levels: project (in the repo, shared with the team) and user (your config, across all your projects). Start with none; run /init when you're ready.

Say it like this

"This is the most important file in the whole system. CLAUDE.md is a plain-English file that holds the rules of your work: what the project is, how you want things done, what to never do. Claude reads it at the start of every session. So instead of re-explaining your rules every time, it starts already knowing them. And because it's an ordinary file, you can share it: put it in the shared project folder and the whole team works from the same rules." (framings.md — skill file as institutional memory: "those rules lived in your senior person's head and walked out the door at six o'clock; this pulls them onto disk so a new joiner writes the same kind of work on day one." Adapt the role to the room.)

Pause, then ask
  • "What do you re-explain to AI — or to a new hire — every single time, that you wish it just knew?"
  • "If your best person left tomorrow, what rules in their head would walk out with them?"

(wait — this lands hard in regulated and professional rooms.)

By background (what goes in the file)
Investigator
the eight-section report rules, "cite every source, never infer", the evidence-gaps rule.
Analyst
the fixed column set, the "no data" rule, "comparison only, no recommendations".
Designer
the filename convention, brand colours by name, "mark silent fields ask client".
Knowledge worker
the CSV schema, "leave absent fields blank", the review-flag rule.
Reporter
the five-section format and the team roster.
Content
the house-voice constraints — no rhetorical questions, no "we", word-count target.
Form-filler
the template sections, "one section per receipt", the totals-reconcile rule.
Outreach
the five-section proposal format and "no invented numbers".
Exec
the four-part brief, "numbers as-is", "state risks factually, don't editorialise".
Watch for

Start with no file. Notice what you keep correcting, then save those corrections — that keeps the file compact and earned, not bloated guesswork. Tell them they can just say "save that to memory" and run /init when ready. This is the bridge to the deep-dive "Introduction to Agent Skills"; the plain-English rules file is the centre of the Praxis method. (train-the-trainer.md — the skill file is the heart of what we teach.)

Key concept — the three CLAUDE.md levels

Verified against the official Claude Code memory docs (June 2026). The spoken script simplifies to two levels (project + user) on purpose; this is the fuller picture for a technical room that asks. The mental model: user file = how I work everywhere, project file = how this codebase works, local file = how I work on this codebase specifically. 1. Project — ./CLAUDE.md. At the repo root (Claude also walks up parent folders). Committed to git, so it's shared with the whole team. Project conventions, build/test commands, code style. 2. Local — ./CLAUDE.local.md. Same folder but gitignored — still scoped to this repo, but personal to you, teammates never see it. Now deprecated in favour of an @path import inside CLAUDE.md pointing at a gitignored file (plays better with worktrees); the old file still loads. 3. User / machine — ~/.claude/CLAUDE.md. In your home dir; applies to every project on that machine for your account. Personal defaults that follow you everywhere (tone, language, "explain before editing"). They stack, most-specific-wins on conflict: user → project → local. Any of them can pull in more files with @path/to/file.md import lines. (Two beyond the three: a subdirectory CLAUDE.md loads on demand when Claude touches that folder; an org can ship an enterprise managed-policy file that outranks even the user file.)

Lesson 9 · Customise

Subagents, send the heavy lifting away

The idea

A subagent does the messy exploration in its own context and returns only the answer. Your main memory stays clean. Create one with /agents — Claude writes the Markdown and YAML for you.

Say it like this

"Some jobs need a lot of digging: reading through half the files to find one thing. If your main session does all that reading, its memory fills up with material you don't need. A subagent fixes that. It's a helper that does the digging in its own separate memory and sends back only the answer, so your main session stays focused on the task. You create one just by asking; Claude writes the setup for you." (Plain framing: it's like asking a researcher 'go find me this' and getting a one-paragraph answer, not their twenty open tabs.)

Pause, then ask
  • "What's a piece of digging you do that means opening twenty tabs and only one line of it matters?"
  • "If someone could go do that and bring back just the answer, what would you hand them?"

(wait)

By background (the digging they'd delegate)
Investigator
"find every mention of this entity across the file set" — answer only.
Analyst
"which responses left this question blank?" — the list, not the reading.
Designer
"scan competitor campaigns before this pitch" — the summary back.
Knowledge worker
"which suppliers use a different invoice format?" — just the answer.
Reporter
"who hasn't submitted an update this week?" — the names, not the trawl.
Content
"what have we already published on this topic?" — the shortlist, cited.
Form-filler
"which receipts don't match any template section?" — the flagged set.
Outreach
"pull the latest on this prospect before I write" — the brief, not the search.
Exec
"which retainers come up for renewal this quarter?" — the list, sourced.
Watch for

This is mainly a context-hygiene tool; don't oversell it as a separate product. The win is your main session stays focused while the grind happens elsewhere. Points to the dedicated "Introduction to subagents" course if they want to go deeper.

Lesson 10 · Customise

Skills, capability loaded only when needed

The idea

A skill advertises itself with a name and one line; Claude loads the full instructions only when it decides to use it. That keeps the context lean. (Contrast with MCP, next slide, which loads every tool definition up front.)

Say it like this

"A skill is a set of instructions for one repeatable task: the steps, the rules, the format, written down once. When that task comes up, Claude loads the instructions and does the job your way. The rest of the time the skill costs almost nothing, because Claude only holds its name and a one-line description. You've already used the built-in skills every time it made you a spreadsheet or a document. The valuable ones are the ones you write yourself, in plain English, about your own work." (framings.md — skill file as institutional memory; this is the same rules-on-disk idea as CLAUDE.md, packaged as a reusable capability. The deck points to "Introduction to Agent Skills" for the deep dive.)

Pause, then ask
  • "What's a task you do the same way every time, where the 'right way' lives in someone's head?"
  • "If that method were written down once, what would you stop having to re-explain?"

(wait — this is the line that earns the upgrade from "AI tool" to "institutional asset".)

By background (the skill they'd build)
Investigator
a Subject Background Report skill (the eight-section PI exemplar).
Analyst
a vendor-comparison skill with fixed columns and the "no data" rule.
Designer
an asset-manifest skill that reads briefs and lists every variant.
Knowledge worker
an invoice-to-CSV skill with a review queue for anything ambiguous.
Reporter
a weekly-briefing skill in the five-section format.
Content
a house-voice draft skill that flags lines that drift off voice.
Form-filler
a receipt-allocation skill that never drops a line and reconciles totals.
Outreach
a proposal skill, one per customer, in fixed five sections.
Exec
an exec-brief skill: revenue, at-risk, decisions, steady.
Watch for

Don't conflate the lean loading mechanic (the engineering point of the slide) with the plain-English rules file that is our method's centre. Both are called "skills". Name the difference or they'll merge. The takeaway for these learners is the second: your method, written down, reused. (train-the-trainer.md — the skill file is the heart.)

Lesson 11 · Customise

MCP, a bridge to everything outside the code

The idea

Most of your context lives in databases, apps and repos. MCP is one open standard that lets Claude Code reach it through tools. Scope it local, user, or project (.mcp.json in the repo). Watch the cost: every server loads its tool definitions whether used or not; a CLI or a skill is often leaner.

Say it like this

"Most of what Claude needs to know doesn't live in one folder. It lives in your email, your project tracker, your databases. MCP is the standard that connects those, so Claude works with your actual data instead of what you paste in. One practical thing to know: every connection takes up a little of its working memory whether you use it or not, so switch off the ones you don't need." (objections.md — IT/compliance: it sees only what you can see; connecting your email doesn't expose anyone else's, and you can revoke it.)

Pause, then ask
  • "Where does the data you'd want it to work with actually live today?"
  • "Which one tool, connected, would kill the most copy-paste in your week?"

(wait)

By background (the connection that earns its place)
Investigator
the document store where case files live — after the IT conversation.
Analyst
the warehouse or drive holding vendor responses.
Designer
the design tools, plus the drive for brand assets.
Knowledge worker
the email and drive where invoices land.
Reporter
the project tracker and chat where status updates live.
Content
the CMS or notes app holding the back catalogue.
Form-filler
the drive or email where receipts arrive.
Outreach
the CRM and email for customer context.
Exec
the drive, chat and email for the board-pack inputs.
Watch for

This is the data-safety gate for almost everyone. Slow down. Give the floor (Claude on the web, no install) and the ceiling (a local model, nothing leaves your network), and for banks and firms frame it as the IT-discovery conversation, not a yes/no. (objections.md — IT/compliance/privacy.) On cost: if the connections get heavy it switches to finding tools on demand, which is less reliable — so prune.

Lesson 12 · Customise

Hooks, the things that must happen, always

The idea

A hook is a rule that runs automatically, every time, with no exceptions. Hooks fire at fixed points in the lifecycle — when you submit, before a tool, after a tool, when Claude stops. Configured in settings.json, checked into the repo. PreToolUse can block.

Say it like this

"Everything else in this session works by asking: you request something, and Claude usually does it. A hook is different. A hook is a rule that runs automatically, every single time, with no exceptions. For example: format every file after it's saved, log every command for the audit trail, block a dangerous action before it runs. The test is simple. If a rule has to hold every time without fail, don't put it in a prompt — put it in a hook." (For these learners the headline is the guarantee, not the syntax: some rules are too important to leave to "usually".)

Pause, then ask
  • "What's a rule in your work that has to hold every time — no exceptions, no 'usually'?"
  • "Where has 'someone forgot the last step' actually cost you?"

(wait)

By background (the always-rule they'd guarantee)
Investigator
log every action for the audit trail; block any report that ships uncited.
Analyst
every output stamped with its sources; block a table with an unexplained blank.
Designer
every export run through the naming convention, automatically.
Knowledge worker
