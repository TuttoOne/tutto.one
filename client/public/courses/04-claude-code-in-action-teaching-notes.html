Claude Code in Action — teaching notes

Side-by-side notes for 04-praxis-claude-code-in-action.html (17 slides). This is the applied course: a real session start to finish — install, point it at a project, make changes and review the diff, then drive and customise it (context control, custom commands, MCP, GitHub) and lock in the must-haves with hooks, ending at the SDK. Course 02 (Claude Code 101) gave the concepts; this one shows them working. Keep the framing on "what this means for your world", not the engineering. The deck is what the room looks at; this is what you say, where you stop, and how each idea lands for the person in front of you. The source is mostly video, so these notes lean on the deck spine plus the four text lessons (setup, project setup, hook gotchas, useful hooks) plus cross-references to course 02 — slides built that way are flagged. Written against the Praxis teaching library. Method: teaching-notes-method.md.

How to use these notes
  • These are guidance, not a script. Teach the person, not the slides.
  • Each teaching slide has a Pause, then ask block. Put the question, then stop. Do not fill the silence. If they freeze, one line: "Take your time, type anything when you're ready, including 'I don't know'." Then wait again.
  • By background gives you a line per archetype (from tutor/scenarios.md). Reach for the one that matches whoever is in the room and ignore the rest. They are a palette, not a checklist to read out.
  • This course names commands and files (@file, CLAUDE.md, /clear, /compact, /context, /mcp, settings.json, PreToolUse). Say them; do not read code or JSON aloud (framings.md — voice). The point of every command is the outcome, not the keystroke.
  • Hold the voice (train-the-trainer.md Part 4): no "great question", no emoji, one term only — Claude Code. Underclaim. Cost is "about twenty dollars a month" and stop.
  • Run the intake first (train-the-trainer.md) so you know which background you're teaching to. This course assumes course 02 has landed; if it hasn't, plant the bridge fast: this is the agent acting in your own files, the durable on-disk version of the browser Claude.

Lesson 1 · Foundation

From autocomplete to a teammate that acts

Flagged: source is video-only; built from the deck slide + course 02 slide 3.

The idea

Coding assistants sit on a spectrum. Autocomplete guesses your next line; a chat assistant answers and you copy it across; an agent reads your project and does the work itself. Claude Code is the agent end.

Say it like this

"There's a spectrum here. At one end, autocomplete — it finishes your line. In the middle, a chat assistant — it answers, and you carry the answer across yourself. At the far end is Claude Code: it reads your files, edits across them, runs the commands, and decides what to do next. Same intelligence you know from the browser, but now it has hands." (Pairs with framings.md — the folder is the memory: the work moves out of a chat you lose and into a place that persists.)

Pause, then ask
  • "Where in your week are you the courier — copying something out of one tool, doing a step, pasting the result back?"
  • "What would change if that middle carrying step just happened?"

Lesson 5 · Get going

Context in: how Claude learns your project

Flagged: source is video-only; built from the deck slide + course 02 slides 5 and 8.

The idea

Claude only knows what's in its context window. You get the right things in before you ask: name a file or folder with @file, paste in errors or logs or images, keep standing rules in CLAUDE.md (read every session), and let it search the repo itself. Be specific — the less it has to guess, the less it wanders and the less each run costs.

Say it like this

"Claude knows exactly what's in front of it and nothing more. So before you ask, you put the right things in front of it: point at a file with the @ sign, paste in an error or a screenshot, keep your standing rules in a file it reads every time, and let it search the folder when it needs to. The skill is being specific — vague prompts cost you, because it goes wandering to fill the gap." (framings.md — context window: the browser chat forgets the beginning once it runs long; here the memory is bounded by your disk, and the rules file keeps working across every file you drop in.)

Pause, then ask
  • "What do you find yourself re-explaining to AI every single time you open it?"
  • "What's the one document it would always need to see to do your task properly?"

Lesson 6 · Get going

Making changes: describe it, review the diff

Flagged: source is video-only; built from the deck slide + course 02 slides 6–7.

The idea

You say what you want in plain English; Claude edits across the files and shows you a diff — exactly what changed. You approve or refine, go round again, and only commit when it's right. You stay in control: every edit is reviewable, and you can steer, undo or redirect before anything lands.

Say it like this

"Here's the part people worry about, and it's the part you have the most control over. You describe the change. It makes the edits and shows you a diff — a side-by-side of exactly what it changed, nothing hidden. You approve, or you correct it and it goes again. Nothing gets locked in until you say so. You're never handing it the keys; you're reviewing every change before it lands." (objections.md — permission: confirm-each- step first, you always check the end, switch to faster modes once the pattern is familiar.)

Pause, then ask
  • "On a task that matters to you, would you rather approve each step, or see the finished result and check it?"
  • "Take the task you named in intake — what would 'done right' have to include for you to trust the change?"

Lesson 7 · Drive & customise

Controlling context: keep the window lean

Flagged: source is video-only; built from the deck slide + course 02 slide 8.

The idea

A long session fills the context window. Three commands keep it focused on what matters now: /clear (wipe it for a new, unrelated task), /compact (summarise but keep the thread on the same task), /context (see what's filling it). Near the limit it auto-compacts; answers drifting is usually a full window.

Say it like this

"Think of its working memory as a desk. Every file it reads, every command it runs, lands on the desk, and the desk has an edge. When you start something unrelated, /clear wipes it clean. When you're mid-task and it's running long, /compact tidies up but keeps the thread. And /context shows you what's taking the space. If answers start drifting, that's usually a full desk." (framings.md — context window: here the memory is bounded by your disk, not a chat that forgets the beginning.)

Pause, then ask
  • "When you've used a chatbot on a long task, have you felt it lose the thread of what you said earlier?"
  • "Which of your tasks are one clean job, and which sprawl across many steps?"

(wait)

The idea

Lesson 9 · Drive & customise

MCP: reach the tools outside your code

Flagged: source is video-only; built from the deck slide + course 02 slide 13.

The idea

Most of what you need lives in other systems — issues, docs, databases, repos. MCP is one open standard that connects Claude Code to them as tools. Scope it local, user or project (.mcp.json in the repo). Watch the cost: every server loads its tool definitions whether you use them or not, so add what you need and disable the rest.

Say it like this

"Your real context doesn't all live in one folder — it's in your email, your project tracker, your databases. MCP is the one standard that plugs those in, so Claude Code can reach your actual data instead of starting cold. One thing to know: each connection costs a little memory up front whether you use it or not, so you turn off what you don't need." (objections.md — IT/compliance: it sees only what you can see; connecting your email doesn't expose anyone else's, and you can revoke it.)

Key concept — MCP servers in GitHub Actions

Verified against the official docs (code.claude.com/docs/en/github-actions and anthropics/claude-code-action docs/configuration.md, June 2026). Not in the spoken script; for the rare room that runs MCP in CI. There's a two-level permission model and both levels are required: 1. Configure the server via --mcp-config inside claude_args (inline JSON or a file path). 2. Allow-list each tool in --allowedTools using the mcp__<server-name>__<tool-name> pattern; the prefix mcp__<server>__* allows every tool from that server. Defining the server alone does nothing — a tool not named in --allowedTools can't be called. That's deliberate defense-in-depth: a misconfigured or hostile server still can't act without explicit per-tool permission. ```yaml

  • uses: anthropics/claude-code-action@v1 with: anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} claude_args: | --mcp-config '{"mcpServers": {"sequential-thinking": {"command": "npx", "args": ["-y", "@modelcontextprotocol/server-sequential-thinking"]}}}' --allowedTools mcp__sequential-thinking__sequentialthinking `` Supporting requirements: a workflow permissions: block (contents, issues, pull-requests, plus id-token: write for Bedrock/Vertex OIDC) and the ANTHROPIC_API_KEY secret. Migration note: the beta allowed_tools input moved to claude_args: --allowedTools` in v1.

Lesson 11 · Hooks & SDK

A prompt is a request. A hook is a guarantee.

The centrepiece of this course. If they take one thing away, it's this.

The idea

Asking Claude to "always run the formatter" is a request it might forget — it sometimes runs, sometimes gets skipped. A hook is a command the harness runs every time at a fixed point, no exceptions. Prompts are probabilistic; hooks are deterministic. If something must happen every single time, don't put it in a prompt, put it in a hook.

Say it like this

"Everything else this session is something you ask for, and usually get. A hook is something that always happens — no asking, no exceptions. The reason it's reliable is that it's run by the machinery around Claude, not by Claude deciding to remember. Format every file. Log every action for compliance. Block a dangerous step before it runs. The rule of thumb: if it has to happen every single time without fail, it doesn't belong in a prompt, it belongs in a hook." (For these learners the headline is the guarantee, not the syntax: some rules are too important to leave to "usually".)

Pause, then ask
  • "What's a rule in your work that has to hold every time — no exceptions, no 'usually'?"
  • "Where has 'someone forgot the last step' actually cost you?"

(wait — making the always-rule explicit is the lesson.)

This is where the system becomes trustworthy at team scale. Don't read JSON aloud; teach the guarantee. (Mirrors course 02 slide 14.)

Key concept — the primary purpose of hooks

To turn what you'd ask Claude to do into what always happens — convert a probabilistic request into a deterministic guarantee. Prompts are run by the model (it usually complies, but "usually" isn't "always"); hooks are run by the harness at a fixed lifecycle point, every time, no exceptions. Rule of thumb: if it must happen every single time without fail, it doesn't belong in a prompt, it belongs in a hook. Three shapes it takes: guarantee an action (format every file, log every call — PostToolUse), block a dangerous one (stop an rm -rf, a commit to main, a read of .env — PreToolUse), inject standing context (SessionStart, UserPromptSubmit). The deeper payoff and the reason this is the course's peak: it's what moves a team from "we'll review it after" to "it can't happen in the first place" — the trust that makes unsupervised work safe.

Lesson 12 · Hooks & SDK

Defining a hook: event → matcher → command

Source: text lesson "Gotchas around hooks" + deck slide. The most technical slide in the course; for non-technical rooms teach the shape, not the syntax.

The idea

A hook is three things in a settings file: which lifecycle event (e.g. before a tool runs), which tool it matches, and the command to run. A PreToolUse hook that exits with a block code stops the action before it happens — that's how you stop a dangerous delete or a commit to the main branch before it lands, not after. Use absolute paths for the script.

Say it like this

"A hook is three simple decisions. When does it fire — for instance, just before a tool runs. What does it apply to. And what command should run. The powerful case is the 'before' hook: it can look at what's about to happen and stop it. So a dangerous delete, or a change to something protected, gets caught before it happens, not cleaned up afterwards. You're moving from 'we'll review it after' to 'it can't happen in the first place'." (Keep it conceptual; this concept does not vary much by domain — see the shared example below.)

Pause, then ask
  • "What's the action in your work that should simply never be allowed to happen by accident?"
  • "Where would 'caught before, not cleaned up after' have saved you a bad day?"

(wait)

By background — one shared example (this slide's mechanic genuinely doesn't vary by domain)

The universal version: a "before" hook that blocks the irreversible mistake — deleting the wrong folder, overwriting the master file, sending before a check passes. For any of the nine, the picture is the same: the thing you most fear doing by accident, made impossible rather than merely discouraged. Watch for

Do not get lost in the settings file. The teachable idea is the gate: some actions should be impossible, not just reviewed. Name absolute paths once (it's a security recommendation) and move on. The how-to-share-it problem is the next slide.

Key concept — which hook blocks a tool call Verified against the official Claude Code hooks docs (June 2026). The blocking hook is PreToolUse — it's the only one that runs before a tool executes, so it's the only one positioned to stop it. (PostToolUse runs after; UserPromptSubmit, Stop, Notification, SessionStart fire at unrelated points.) It receives the tool name and its input, so you gate on conditions — match Bash against a deny-list, block any Edit/Write touching .env, secrets, or prod paths. Two ways to block
  • Exit code 2 → tool call blocked; the hook's stderr is returned to Claude as the reason.
  • JSON on stdout with a permission decision (the structured form the slide doesn't show): ``json { "hookSpecificOutput": { "hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": "Editing of .env files is not allowed" } } ` "allow" auto-approves, "deny" blocks, "ask"` prompts the user.

Lesson 13 · Hooks & SDK

Hooks in practice: share them, debug them

Source: text lessons "Gotchas around hooks" + "Useful hooks!". Two real, concrete problems — keep them grounded.

The idea

Two practical problems the course solves. One — sharing hooks across machines: absolute paths are recommended for security, but your path isn't my path, so the project ships an example settings file with a $PWD placeholder that the setup step expands into real local paths. Two — knowing what a hook actually receives: the input on stdin changes per event and per tool, so log it first with a simple command before you write the real one. There are nine lifecycle events in all.

Say it like this

"Two real-world snags. First, sharing: the secure way to write a hook uses the full path to a script, but my full path won't match yours, so the project uses a placeholder that gets filled in automatically when each person sets up. That's how a team shares the same guarantees without hand-editing paths. Second, debugging: a hook gets fed information, and the shape of it changes depending on what triggered it — so the trick is to log it first and look, then write the real rule against what you actually saw." (Concrete, not abstract: this is the "measure twice, cut once" of hooks.)

Pause, then ask
  • "When you've shared a working setup with a colleague before, what broke when it landed on their machine?"
  • "Where in your work do you wish you could see exactly what a process received before it acted?"

(wait)

By background — one shared example (this is tooling hygiene, not domain logic)

The shared picture: a team wants the same guarantee on every machine — say, "every output gets logged for the audit trail" — and the placeholder-and-setup trick is what lets one person write it and everyone inherit it without breaking on their own paths. For a regulated room (Investigator, Analyst, Exec) lean on the audit-trail framing; for the rest, "everyone gets the same safety rail" carries it. The debugging half is the same for all nine: look before you build.

Watch for

This is the most "engineering" of the hook slides. Most non-technical learners won't author this themselves — and that's the honest reason a Praxis trainer or a developer sets the shared settings up once, after which the team just inherits it. Frame it as "this is the part someone does for the team, once" rather than a day-one solo task.
