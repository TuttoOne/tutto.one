Introduction to Model Context Protocol — teaching notes

Side-by-side notes for 07-praxis-introduction-to-model-context-protocol.html (14 slides). This is the most technical course in the set: it is built for engineers wiring MCP servers, clients, tools, resources and prompts. Our job is to teach the idea to the nine non-technical archetypes without selling them the plumbing. Keep the framing on "what this means for your data and your tools", not the JSON-RPC. Course 01 slide 10 (Connectors / MCP) and course 02 slide 13 (MCP) already pitch MCP to these learners — match that framing, this is the longer version. The deck is what the room looks at; this is what you say, where you stop, and how each idea lands for the person in front of you. Written from the deck and the Praxis teaching library. Method: teaching-notes-method.md.

How to use these notes
  • These are guidance, not a script. Teach the person, not the slides.
  • Each teaching slide has a Pause, then ask block. Put the question, then stop. Do not fill the silence. If they freeze, one line: "Take your time, type anything when you're ready, including 'I don't know'." Then wait again.
  • By background gives you a line per archetype (from tutor/scenarios.md). Reach for the one that matches whoever is in the room and ignore the rest. They are a palette, not a checklist to read out.
  • This course is heavy on protocol mechanics (servers, clients, transports, decorators). Several slides do not vary by professional domain — where that is true, the note says so and gives one shared example rather than nine contrived ones. Don't read code aloud (framings.md — voice); the point of every slide is the outcome, not the syntax.
  • The one thing every non-technical learner must leave with: MCP is the single standard that plugs Claude into the tools you already use; it sees only what you can see; it is scoped and revocable. Data-safety is the spine of this course for these rooms. It comes up earliest and hardest on slides 3, 8 and 13 — slow down there.
  • Hold the voice (train-the-trainer.md Part 4): no "great question", no emoji, one term only — Claude Code. Underclaim. Cost is "about twenty dollars a month" and stop.
  • Run the intake first (train-the-trainer.md) so you know which background you're teaching to. If the room hasn't done courses 01 and 02, plant the bridge: the connectors and MCP they met there are what this course opens up.

One protocol, so any AI app can reach any tool or data source

The idea

Set the frame: eleven ideas, one per screen, and the watching is the lesson. This course explains the wiring under "connect your tools" — but for these learners the takeaway is not how to build it, it's what it is and why it's safe.

Say it like this

"Eleven ideas, one screen each. In Claude 101 we said Claude can plug into the tools you already use. Open with

The intake answer: the tool or system where their real work lives — the case store, the inbox, the CRM, the drive. Name it, and promise you'll come back to it: by the end they'll know exactly what connecting it does and doesn't expose.

Lesson 1 · Foundation

M×N integrations become M+N

The idea

Without a standard, every app wires up to every tool by hand — the tangle grows with both sides. MCP is the standard connector ("USB-C for AI"): build to it once and every compliant tool just works. M×N custom integrations become M+N.

Say it like this

"Before this, every AI app had to be wired by hand to every tool — your email, your drive, your tracker — over and over, a tangle that grows with both sides. MCP is one standard, like USB-C for AI: build to it once and every tool that speaks it just works. That's why connecting things to Claude stopped being a custom job." (Mirrors course 01 slide 10 — connectors, the one standard behind them.)

Pause, then ask
  • "Think of the tools you use that don't talk to each other today — where do you do the carrying by hand between them?"
  • "If those tools all spoke one language, which connection would you want first?"

Lesson 2 · Foundation

Host, client, server: one client per server

The idea

The app you use is the host (Claude Code, Desktop, Cursor). Inside it, each client holds one connection to one server, and the server wraps the real tool or data. Messages travel as JSON-RPC over a transport — stdio for local, HTTP for remote.

Say it like this

"Three words worth knowing, because the rest hangs off them. The host is the app you're in — Claude Code, the desktop app. The server is the thing that wraps a real tool or data source, your drive or your tracker. And a client is one private line between them, one client to one server. The host can hold many of these lines at once." (Don't dwell on JSON-RPC or transports — name them once, on the caption, and move. They don't change anything for a non-technical learner.)

Pause, then ask
  • "How many separate systems would you want Claude to reach in a normal week — one, or several at once?"
  • "Which of those would you trust it to read, and which would you want to keep walled off?"

(wait)

the case store, plus a sanctions/screening source — separate lines.

the responses drive and the data warehouse, kept distinct.
Designer
the design tool and the brand-asset drive, two connections.
Knowledge worker
the inbox and the accounts drive.

the project tracker and the team chat.

the CMS and the analytics source.

Watch for

"One client per server" is the seed of the safety point: each connection is separate and named, so you grant and revoke them one at a time. You don't open a floodgate, you run individual lines you control. (Sets up slide 13 — scoped and revocable.) Keep the transport detail off the floor unless a technical person asks. Lesson 3 · Foundation

A server is a few lines to start

The idea

The Python SDK's FastMCP does the protocol plumbing. You create a server, register capabilities with decorators, and run it over a transport (stdio local, HTTP remote). Same server code either way — the transport is just how messages travel.

Say it like this

"This slide is for the builders in the room: standing up a server is small. The SDK handles the protocol; you write a few ordinary functions and mark them as capabilities. For everyone else, the takeaway is only this — the people who make these connections do it in a handful of lines, which is why so many tools already have one." (One shared example below; this is a mechanics slide, it does not vary by domain.)

Pause, then ask
  • "When you hear 'someone could connect this in an afternoon', does that change which of your tools you'd ask about?"

(wait)

By background

This is a purely mechanical slide — building a server does not vary by profession, so don't force nine. One shared framing for the room: "Whatever your tool, the connector is small to build and many already exist. Your job isn't to build it; it's to know which one you want and what it should be allowed to see." Then move on.

Watch for

Don't get drawn into uv, FastMCP, stdio vs HTTP with a non-technical room — it's noise to them and the slide is inferred from the course title, not captured prose (sanity-check against the video for a technical audience). Keep it to "small to build, many already exist" and move. For the IT-restricted: a local server (stdio) runs on your own machine, nothing leaves it — that's the privacy ceiling in miniature. (objections.md — IT/compliance: local model, nothing leaves your network.)

Lesson 4 · Tools

Actions the model can choose to call

The idea

A tool is a function the server exposes; its name, description and typed arguments become a schema the model reads, and the model decides when to call it. Tools are the verbs — they do things, they have side effects. Model-controlled: the model picks the moment, not the app or the user.

Say it like this

"The first of three pieces. A tool is an action Claude can take — send the email, run the search, update the record. The verbs. The key word is who decides: Claude does. It reads what each tool is for and chooses when to use it, the way a capable colleague decides which step to take next. That's why we call tools model-controlled." (Pairs with course 02 slide 3 — an agent acts, it doesn't just hand you text. A tool is how it acts.)

Pause, then ask
  • "What's an action — not a lookup, an action — that you'd be comfortable letting it take on your behalf?"
  • "And what's one you'd want to keep your hand on, every time?"

(wait)

By background (the action they'd expose as a tool)
Investigator
run a sanctions/PEP screen on a named subject — read-only, low risk.
Analyst
pull a fresh figure from the warehouse into the comparison.
Designer
push an export to the asset library under the naming convention.
Knowledge worker
file an extracted invoice into the accounts system.
Reporter
post the finished briefing to the team channel.
Content
schedule a draft into the CMS as unpublished.
Form-filler
write an allocation back to the filing record.
Outreach
create a draft email per customer — drafted, never auto-sent.
Exec
log a renewal decision against the account.
Watch for

Tools do things and have side effects — this is exactly where "what if it does something I don't want?" lives. The answer is the permission model from course 02 slide 6 (Shift + Tab, approval first): the model can choose to call a tool, but you decide whether it's allowed to. Draft, don't auto-send, until trust is earned. (objections.md — permission / "scary to let it".)

Lesson 5 · Tools

Test the server before wiring it to an app

The idea

The Inspector connects straight to your server with no model involved. List what it exposes, call each tool by hand, read the raw response. Debug the server in isolation first; if it lists and calls cleanly, a later problem is in the client wiring.

Say it like this

"This is a builder's slide: before you let Claude near a new connection, you test it on its own — does it list its tools, does each one return cleanly. A plain quality check on the plumbing. For everyone else, the point is reassuring: connections get tested in isolation before they're trusted, the same way you'd test a new process on dummy data before you run it for real."

Pause, then ask
  • "Before you trust a new process at work, what's your version of testing it on dummy data first?"

(wait)

By background

A mechanics slide — testing a server doesn't vary by profession. One shared framing: "Whatever the connection, it gets proven in isolation before it touches your real work — the discipline you'd want anyway." Tie it back to the Praxis habit they'll recognise from the demo: test on dummy data, then run for real. Don't force nine.

Watch for

Inferred slide (video-only source) — the Inspector detail is from canonical MCP teaching, not captured prose; verify for a technical room. For non-technical learners, keep it to "connections are tested before they're trusted" and move. Resist the urge to demo the Inspector UI; it adds nothing for this audience.

Lesson 6 · Tools

The client feeds tools to the model, in a loop

The idea

The client lists the server's tools, hands their schemas to Claude, runs whatever Claude asks for, and feeds the result back — looping until there's an answer. This is the same agentic loop a plain chat window doesn't have; MCP is just how the tools reach it.

Say it like this

"Here's the loop you saw in Claude Code 101, now with MCP feeding it. Claude is offered the tools, asks for one, the server runs it, the result comes back, and it goes round again until the job's done. A chat window can't do that — it answers and waits. MCP is simply how the tools get into that loop." (Mirrors course 02 slide 4 — the agentic loop; this is the loop reaching outside the folder.)

Pause, then ask
  • "Where in your week are you the courier — taking a result out of one tool, doing a step, carrying it into another?"
  • "What would change if that middle carrying just happened, across both tools at once?"

(wait)

Lesson 7 · Resources & prompts

Data to pull in, addressed by URI

The idea

A resource is read-only data the server exposes at an address (a URI like docs://documents). No side effects: think GET, not POST. Direct resources return a collection; templated ones take a parameter to fetch exactly one item.

Say it like this

"The second piece. Where a tool does something, a resource just provides something — a document, a record, a list — at a named address, read-only. Nothing changes when you load it; it's safe to read any time. The whole list, or one item by name. Think of it as the read-only side: fetching, never altering." (Contrast it explicitly with the tools slides — same server, but a resource only reads.)

Pause, then ask
  • "What's the reference material you'd want Claude to be able to read, but never change?"
  • "Is it usually the whole set you reach for, or one specific item at a time?"

(wait)

the case file set, and any one document by reference — read, never edit.
Analyst
the full set of vendor responses, or one provider's by name.
Designer
the brief set and the brand-token sheet, read-only.
Knowledge worker
the inbox of invoices, or one invoice by number.
Reporter
the week's updates, or one team member's note.

Read-only is a safety point worth naming: a resource cannot alter your data, only surface it. For regulated rooms this is the comfortable on-ramp — connect the read side first, before any tool that does things. Don't drown them in URI syntax; "a named address, read-only" is enough. Lesson 8 · Resources & prompts

The app decides which resources to load

The idea

Unlike tools, the model doesn't reach for resources. The application — often the user — chooses what context to bring in, usually surfaced as @-mentions you pick from. Application-controlled. Same server, two different control models: a tool is the model's to call, a resource is the app's to load.

Say it like this

"Here's the difference that matters for trust. A tool, Claude chooses to use. A resource, you choose to bring in — usually by picking it from a list, an @-mention. Claude doesn't go rummaging through your data; it sees a resource only when you, or the app, hand it over. Same connection, but you hold the gate on what's read." (This is the heart of the safety story — say it slowly.)

Pause, then ask
  • "How would you feel about deciding, each time, exactly which document Claude gets to see — rather than it deciding?"
  • "Which of your sources would you only ever hand over deliberately, one item at a time?"

(wait)

the specific subject's file for this matter — chosen, not browsed.

the one provider's response under review this session.
Designer
the brief for the campaign in hand.
Knowledge worker
the month's invoice folder, picked when they start the batch.

this week's updates, selected for this briefing.

the two past posts that set the voice for this draft.

Watch for

This is the single most reassuring slide for an IT-restricted or regulated room: the model does not help itself to your data — you, or your app, decide what it sees, item by item. This is "it sees only what you can see" made concrete: it sees what you hand it. Pair with the floor/ceiling for banks and firms — web with no install at the floor, a local model at the ceiling — and frame connecting anything as the IT-discovery conversation, not a switch you flip alone. Lesson 9 · Resources & prompts

Reusable templates the author ships

The idea

A prompt is a tested, parameterized template the server exposes, so the right wording is baked in instead of reinvented each time. The author tunes it once; everyone else just calls it and gets the good version. Hard-won phrasing moves out of people's heads and into the server.

Say it like this

"The third piece. A prompt here isn't what you type — it's a tested template someone wrote once and packaged, so the good wording is built in. The expert tunes it; everyone else just runs it and gets their standard. If that sounds familiar, it's the same idea as the skill file: the rules that lived in your best person's head, written down so the work comes out their way every time." (framings.md — skill file as institutional memory: "those rules lived in your senior person's head and walked out the door at six o'clock; this pulls them onto disk so a new joiner writes the same kind of work on day one." Adapt the role to the room.)

Pause, then ask
  • "What's a task you do the same way every time, where the 'right way' lives in someone's head?"
  • "If that wording were written down once and everyone could just run it, what would stop drifting?"

(wait — this lands hard in regulated and professional rooms.)

Lesson 10 · Resources & prompts

Prompts surface as slash commands

The idea

The client lists the server's prompts and offers them to the user; pick one, fill the arguments, and it expands into the full message. User-controlled: the user triggers it deliberately, not the model and not the app. If you've used a slash command in Claude Code, you've used an MCP prompt.

Say it like this

"And this is how you reach one: it shows up as a slash command. You type the slash, pick the one you want, answer a question or two, and it expands into the full expert wording, ready to run. You're in control — you trigger it, deliberately. If you've ever used a slash command in Claude Code, that's exactly this." (Tie to their own experience: the /plato they ran to get here is a prompt surfaced as a slash command.)

Pause, then ask

Lesson 11 · Recap

Three primitives, three owners

The centrepiece. If they take one thing away, it's this.

The idea

The whole protocol in one picture: tools (model-controlled, actions the model calls), resources (application-controlled, data the app loads), prompts (user-controlled, templates the user triggers) — all exposed by a server, reached by a client inside your host, over JSON-RPC on stdio (local) or HTTP (remote). Get the owners straight and the rest follows.

Say it like this

"If you keep one thing today, keep this. MCP exposes three things, and the only thing you really need to remember is who controls each. Tools — actions — the model chooses to call. Resources — data — you or the app choose to load. Prompts — templates — you trigger, deliberately. One standard, three pieces, three owners. And the reassurance under all of it: every connection is one you grant, scoped to what you can already see, and you can revoke it." (Mirrors course 01 slide 10 and course 02 slide 13 — the one standard, scoped and revocable, it sees only what you can see.)

Pause, then ask
  • "Of those three — actions Claude takes, data you hand it, templates you run — which feels most useful in your work, and which feels like the one to be careful with?"
  • "Knowing it sees only what you hand it and you can revoke any connection — does that change which tool you'd connect first?"

(wait — their answer is the use case you build the next conversation around.)
