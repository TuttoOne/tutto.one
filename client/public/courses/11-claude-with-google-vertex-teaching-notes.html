Claude with Google Vertex — teaching notes

Side-by-side notes for 11-praxis-claude-with-google-vertex.html (19 slides — the longest deck in the set). This is a developer/infrastructure course: the same concepts as the API and Bedrock courses, but Claude running inside your own Google Cloud. The Praxis translation throughout is one idea: where the model runs is the data-residency story. Vertex is the "ceiling" option from the floor-and-ceiling framing — Claude runs in your Google Cloud tenancy and your data stays in your environment (objections.md — IT/compliance/privacy). Written from the deck and 11-claude-with-google-vertex-lessons.txt (which is video-only bar the one "Vertex AI Setup" text lesson — the deck is the depth source here), against the Praxis teaching library. Method: teaching-notes-method.md.

How to use these notes
  • Guidance, not a script. Teach the person, not the slides. Nineteen slides is a lot — keep each block tight and let the spine on slide 2 carry the shape so nobody feels lost.
  • Every teaching slide has a Pause, then ask block. Put the question, then stop. Don't fill the silence. If they freeze: "Take your time, type anything when you're ready, including 'I don't know'." Then wait again.
  • By background gives a line per archetype (tutor/scenarios.md). Use the one that matches the room; the rest are a palette, not a checklist. This is infrastructure territory, so several mechanical slides (gcloud auth, the request shape, MCP plumbing) don't vary by domain — there the notes give one shared example and say so, then tie the headline concept back to the learner's world. Don't force nine contrived ones.
  • The audience that pays for this course is the regulated one — the Investigator, the Analyst, the Exec whose IT team blocked the web app. Keep returning to "your data stays in your cloud". For everyone else, the honest framing is: this is the engine room, useful to see once so you trust what's under Claude Code.
  • Hold the voice (train-the-trainer.md Part 4): no "great question", no emoji, one term — Claude Code. Underclaim. Cost is "about twenty dollars a month" and stop. Don't read code aloud.

Models

One family, three sizes

The idea

One Claude family on a single axis: Haiku fastest and cheapest, Sonnet the balanced default, Opus the most capable. You pick per task, not once forever, and the same code calls any of them — you change one model string.

Say it like this

"Three sizes, same family. Haiku when volume bites and the work is simple. Sonnet for most everyday building. Opus when the task is genuinely hard. The request

Every call is a Messages request

The idea

One shape underneath everything: a model, a system prompt, a list of messages, and a few limits. Claude replies with content blocks — streamed token by token if you ask. Streaming changes nothing about the request, only how the answer arrives.

Say it like this

"Strip away the surface and every single call to Claude is the same shape: which model, a standing brief, the conversation so far, and a couple of limits. It answers in blocks. If you want the words to appear as they're written rather than all at once, you switch on streaming — same request, the reply just trickles instead of landing."

Pause, then ask
  • "Does it surprise you that there's one simple shape under everything Claude does?"
  • "Where would you rather see an answer build live, versus wait and get it complete?"

(wait)

By background

This is a mechanical slide — the request shape is identical whatever the domain, so here is one shared example rather than nine: think of it as the standing order form. You always fill in the same fields — who's serving (model), the house rules (system), the conversation (messages), and how long the answer can run (limits). What you write into those fields is where your work differs; the form never changes. Connect it to their world only at the headline level: "the 'standing brief' field is where your team's rules will eventually live — that's the system prompt, two slides on."

Watch for

Streaming is a UX nicety, not a capability. Don't let anyone think a streamed answer is smarter or different — it's the same answer, delivered differently.

6
Multi-turn

The API has no memory

The idea

Each call starts cold. A "conversation" is just you re-sending the whole history every time; the model never remembers the last turn on its own. So you carry the state — the message list only grows, and so does cost (prompt caching, slide 13, softens that). The flip side: you are in full control of what the model can and cannot see.

Say it like this

"Here's something that surprises people. The model has no memory. Every call starts from nothing. What looks like a conversation is you handing it the whole transcript again each turn. That's why long chats get slower and pricier — it re-reads everything every time. And it's exactly why you're in full control: nothing reaches the model unless you put it there."

Pause, then ask
  • "If the model only ever sees what you hand it, what does that tell you about who controls the data?"
  • "Where in your work would 'it only knows what I explicitly gave it' be reassuring?"

(wait)

By background ("you control exactly what it sees")
Investigator
only the documents you pass enter the model — nothing from the wider case system leaks in.
Analyst
the model sees the submissions you hand it and nothing else from the warehouse.
Designer
only the briefs in this batch; other clients' work never enters the call.
Knowledge worker
just this month's invoices, not the whole finance drive.
Reporter
only the updates you collected, not the team's full inbox.
Content
only the past posts you chose as the voice sample.
Form-filler
only the receipts for this filing period.
Outreach
only this customer's file — no cross-contamination between accounts.
Exec
exactly the board inputs you selected, nothing broader.
Watch for

This pairs with slide 4 to fully answer the data fear: it runs in your cloud and it only ever sees what you hand it. For regulated rooms, that's the two-part reassurance. (objections.md — IT/compliance; "where is the AI".)

Control

Four knobs shape the output

The idea

Before clever prompting, four dials the API hands you directly. System prompt: the role and rules it holds for every turn — the most leverage. Temperature: 0 steady and repeatable, 1 loose and varied. Structured output: ask for JSON you can parse, not prose. Stop and length: cap and end the reply. Reach for the knobs first.

Say it like this

"Four dials, and most people skip them and go straight to fancy prompting. The big one is the system prompt — the standing role and rules. Then temperature: turn it down for anything you need the same every time, turn it up for brainstorming. Then asking for clean data instead of prose. Then caps on length. A clear brief and a couple of these solve most 'it won't behave' problems before you've done any real prompt engineering."

Pause, then ask
  • "In your work, which matters more: an answer that's the same every time, or one that's creative and varied? That's the temperature dial."
  • "What standing rules would you want it to hold on every single task — that's your system prompt?"

(wait)

By background (temperature low vs high, and the standing rule)
Investigator
temperature near zero — extraction and citation must be repeatable; standing rule "cite every source, never infer".
Analyst
low — the comparison must reconcile run to run; rule "mark blanks 'no data'".
Designer
high for concept generation; low for spec extraction. Standing rule: brand tokens by name.
Knowledge worker
near zero — invoice extraction must be deterministic; rule "leave blanks blank".
Reporter
low for the briefing; rule "cite who said what".
Content
higher for drafting voice; rule "follow the house structure".
Form-filler
zero — allocation must be identical each cycle; rule "one section per receipt".
Outreach
moderate — some variety per customer; rule "only numbers from the file".
Exec
zero for the brief; rule "facts, not editorial".
Watch for

Temperature is the most-misread knob. Lower it for extraction, classification, anything you'll parse; raise it for ideas and copy. People assume "higher = better"; it's "higher = looser", which for regulated work is worse, not better.

The eval loop

Don't eyeball it, measure it

The idea

A prompt that "seems fine" on three examples breaks on the fourth. An eval makes "better" a number you can move on purpose: a prompt, a test set with answers, a run over every case, a grade. Code-based grading where the answer is checkable; model-based where quality is a judgement call. Claude can even generate the test set.

Say it like this

"Here's the discipline that separates a hobby from a system. You don't decide a prompt is good by reading three answers and nodding. You build a set of test cases, run the prompt over all of them, and score the results. Now 'better' is a number you can move. Some things you grade with code — a date is right or wrong. Some need judgement, so you have Claude grade them. Either way, you've got a dial, not a hunch."

Pause, then ask
  • "How do you know today whether a process is working — gut feel, or something you can point to?"
  • "What would you want to measure to trust that this does your task right every time?"

(wait — this is the human-premium moment for regulated rooms: you set the standard it's graded against.)

By background (what "graded right" means for them)
Investigator
every claim has a source and the Evidence Gaps section is never empty — code can check both.
Analyst
every cell cites a file, "no data" is honest — code-checkable; comparability is a judgement call.
Designer
every required asset present, specs met — code; on-brand-ness needs an eye.
Knowledge worker
totals reconcile, no field invented — code-checkable.
Reporter
five sections present, nothing misattributed — partly code, partly judgement.
Content
within word count — code; on-voice — model-graded against the past posts.
Form-filler
totals reconcile, nothing dropped — pure code grading.
Outreach
no invented numbers, subject line never a question — code-checkable.
Exec
one page, every decision has an owner and date — code; tone judged.
Watch for

This is where to plant the "software around the AI catches what the AI alone can't" idea. The eval is the inspector. It also calms the hallucination fear: you don't hope it's right, you measure it. (objections.md — hallucinate / make stuff up.)

Four techniques

Most prompting is four moves

The idea

When the eval says the prompt is the problem, four fixes carry the load, roughly in order of return: be clear and direct (say exactly what you want, no hinting), be specific (spell out format, length, edge cases), use XML tags (fence the parts so it can't confuse them), and show examples (two or three; it copies the pattern). The model isn't a mind-reader — vagueness costs more, not less.

Say it like this

"When the prompt is the weak link, four moves fix most of it. Say exactly what you want, no hinting. Be specific about the shape and the edge cases. Fence off the different parts so it doesn't mix them up. And the strongest one, the one people skip: show it two or three worked examples and let it copy the pattern. Telling is good; showing is better."

Pause, then ask
  • "When you've asked AI for something and it disappointed you, were you being specific, or hoping it would read your mind?"
  • "What's an example of 'good' you could show it, instead of describing?"

(wait)

By background (the move that matters most for them)
Investigator
show an example report — the format and citation style carry everything.
Analyst
be specific — name the columns and the "no data" rule exactly.
Designer
show examples — one finished asset beats a paragraph of description.
Knowledge worker
be specific — the CSV schema and "leave blanks blank".
Reporter
show an example briefing in the five-section format.
Content
show examples — paste two past posts for the voice.
Form-filler
be specific — the template sections and the one-section-per-receipt rule.
Outreach
show one finished proposal as the pattern.
Exec
be clear and direct — "one page, facts not editorial, every decision owned".
Watch for

Examples are the highest-return move and the one people skip because it feels like more work up front. It isn't — it's less rework later. Same lesson as the Claude 101 and AI Fluency courses; this is consistent across the whole programme.

The tool-use loop

Claude can't run code, it asks you to

The centrepiece. If they take one thing away, it's this loop.

The idea

This loop is the engine under tools, agents, MCP and computer use. The model never executes anything itself: you define tools (name + schema), Claude decides one is needed (stop_reason: tool_use), your code runs the real function, you return the result, and Claude reads it and continues or answers. A tool is just a function plus a description of when to use it. Once you can run this loop, "an agent" is only this loop left running until the job is done.

Say it like this

"This is the single most important idea in the back half. Claude can never actually do anything by itself. It can't run code, send an email, touch a file. What it does is ask: 'please run this function with these inputs'. Your code runs it, you hand back the result, and it carries on. That's the whole loop. And here's the punchline: an 'agent' isn't a new thing — it's just this loop, left running until the job's done."

Pause, then ask
  • "Does it change how you feel about safety to know the model can only ask to act, never act on its own?"
  • "In your work, what's an action you'd want it to take — and would you want to approve each one, or let it run?"

(wait — the second question surfaces the autonomy fear; let it.)

Built-in tools

Some tools you don't have to build

The idea

You write your own functions, but Anthropic ships ready-made tools Claude already knows how to call — web search (live results with sources to cite), a text editor (view and edit files by line), structured data via a tool schema (forces clean JSON) — plus a batch path for thousands of calls, async and roughly half the cost. Two families: tools you run (your functions) and tools Anthropic runs for you. Batch isn't a tool — it's how you submit a pile of requests when latency doesn't matter and cost does.

Say it like this

"You don't have to build everything. Some tools come ready-made: live web search that hands back sources, a file editor, and a way to force clean structured data instead of prose. And when you've got thousands of jobs to run rather than one, there's a batch lane — slower, but about half the price. Two kinds of tools, then: the ones you write, and the ones Anthropic already wrote for you."

Pause, then ask

The RAG flow

Give the model your data at question time

The idea

Claude doesn't know your documents. RAG fetches the few relevant pieces and pastes them into the prompt, so the answer is grounded in your sources. Ahead of time you index your data (documents → chunks → embeddings → a vector store); at question time you retrieve the top few nearest chunks, combine them with the question into one augmented prompt, and Claude answers grounded in your material. The model's job never changes — RAG is about putting the right paragraphs into the prompt before it ever sees the question.

Say it like this

"The model doesn't know your documents. RAG is how you fix that without retraining anything. Ahead of time you file your documents so they're searchable. Then when a question comes in, you grab just the handful of relevant passages and hand them to Claude along with the question. It answers from your sources, not from general knowledge. The model never changes — you're just feeding it the right pages at the right moment."

Pause, then ask
  • "What's the body of documents you'd want it to answer from — your documents, not the internet?"
  • "Today, when you need an answer that's buried in those documents, how long does finding it take?"

(wait)

13
Making it good

Naive retrieval misses, here's the ladder

The idea

Most RAG fails at the "retrieve" step: it pulls the wrong chunks. Each rung lifts what comes back before Claude sees it. Embeddings find meaning ("similar idea"); BM25 finds keywords ("exact terms, IDs, code"); hybrid merges both; reranking re-sorts by relevance; contextual retrieval prepends a line saying where each chunk came from, because lone chunks lose their thread. Start simple — embeddings alone often suffice.

Say it like this

"When RAG disappoints, it's almost never the answer — it's that the wrong passages got pulled in. So there's a ladder. Search by meaning catches 'the same idea in different words'. Search by keyword catches exact terms, names, codes. Combine them. Re-sort what comes back. And the clever one: before filing each passage, tag it with where it came from, because a paragraph ripped out of context loses its thread. Start simple. Climb the ladder only when retrieval is actually missing."

Pause, then ask
  • "In your documents, do answers hinge on meaning, or on exact terms — names, reference numbers, codes?"
  • "When you search your own files today, what does it fail to find that you wish it would?"

(wait)

both — meaning for themes, keywords for exact metric names and provider IDs.

Native capabilities

Built in, no extra plumbing

That last one matched with RAG is powerful — your documents in, every answer footnoted."

15
Prompt caching

Pay once for the part that repeats

The idea

If the front of every request is the same — a long system prompt, a tool list, a big document — cache it. The first call writes the cache at full price; later calls read the same prefix back at roughly a tenth of the price, and faster. The rules that bite: the prefix must be byte-identical, clear a minimum length, and the cache lasts a few minutes idle. Put the stable stuff first, the variable stuff last. That ordering is good architecture anyway.

Say it like this

"If the same big chunk sits at the front of every request — your standing rules, a reference document, a tool list — you can cache it. You pay full price once, then later calls read it back at about a tenth of the cost, and quicker. The discipline it forces is exactly the right one anyway: stable context up front, the user's changing input at the end. Get that order right and the cache pays for itself." (Ties back to slide 6: this is what softens the cost of re-sending the whole history every turn.)

Pause, then ask
  • "What's the big unchanging block that would sit at the front of every one of your requests — the rules, a reference document?"
  • "Does it matter to you that the cost of the repeated part drops to almost nothing?"

Workflows vs agents

Two ways to put it to work

The idea

A workflow follows a path you fixed in code (chain, route, parallel). An agent decides its own path at runtime: act, observe, decide, until done. The choice is simply: can you predict the steps in advance? Default to a workflow — predictable, cheaper, easy to debug. Reach for an agent only when the path genuinely can't be known ahead of time. That freedom is also the cost.

Say it like this

"Two ways to put this to work. A workflow is a path you lay down in advance — do this, then this, then this. Predictable, cheap, easy to fix when it breaks. An agent decides its own path as it goes, looping until the job's done. The honest default is the workflow. Reach for an agent only when you genuinely can't know the steps ahead of time — because that freedom is also what makes it harder to predict and pricier to run."
