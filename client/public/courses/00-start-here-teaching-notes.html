Start Here — teaching notes

Side-by-side notes for 00-praxis-start-here.html (13 slides). The deck is what the room looks at; this is what you say, where you stop, and how you make each idea land for the person in front of you. This is the prelude to the whole library: the idea, the proof, and how they find their own use case. Written from the deck against the Praxis teaching library. Method: teaching-notes-method.md.

How to use these notes
  • These are guidance, not a script. Teach the person, not the slides.
  • Each teaching slide has a Pause, then ask block. Put the question, then stop. Do not fill the silence. If they freeze, one line: "Take your time, type anything when you're ready, including 'I don't know'." Then wait again.
  • By background gives you a line per archetype (from tutor/scenarios.md). Reach for the one that matches whoever is in the room and ignore the rest. They are a palette, not a checklist to read out.
  • The proof slides (6 to 10) are real systems. Tell them as real: two are Tutto's own, one is a client's. Conviction comes from "I run my business on this," not from a feature list.
  • Hold the voice (train-the-trainer.md Part 4): no "great question", no emoji, one term only, Claude Code. Underclaim. Cost is "about twenty dollars a month" and stop.
  • Run the intake five questions first (train-the-trainer.md) so you know which background you're teaching to before slide 1.

Praxis, start here

The systems I build, and how you build them too

The idea

Set the frame: this is a short tour in three parts, not a lecture. The idea, the proof, then their turn. The watching is the lesson; you will keep handing it back to them.

Say it like this

"This is a quick tour in three parts: the idea behind how I build, real systems already running, then how you'd find yours. Don't try to remember it all. The point today is to see that it's real and that it's within your reach."

Open with

The intake answer they gave you. Name the one repetitive task they said eats their week, and promise you'll point straight at it on the use-case slide near the end.

The idea

Software is exact, AI is likely, pair them

The idea

Software is deterministic, the same result every time. AI is probabilistic, it produces what's likely to help. Claude Code is the pairing: you talk in plain English, it writes the code that runs the same way every time.

Say it like this

"Two different things here. Normal software does exactly what you tell it, the same way every time. AI doesn't follow rules, it produces what's likely to be useful. Claude Code is the marriage of the two: you talk to it in plain English, and it writes the code that does the work, the same way every time. Think of it as an Excel formula that now lives in your folder." (tutor/framings.md, Excel formula; Claude as translator.)

The idea

It gets better the more you use it

The idea

The return people miss. The user shows the system what it got wrong, the rules sharpen, and ten percent to fix becomes five, becomes one. A bought tool is as good as it will ever be on day one; a system you teach keeps improving, and the time saved grows.

The test for a first use case: a task that touches several systems, comes out the same shape every time, and is costly when it's wrong. Score on all three and start there, this afternoon. The honest economics: about twenty dollars a month, ninety percent of the way then finish by hand, and the only scarce thing is a guide.

The honest economics: about twenty dollars a month, you'll get ninety percent of the way and finish the last ten by hand, and the only scarce thing is someone who has done it before, not the software."
