Evals: proving the output is good

A script can give you the same output every time and still be wrong every time. It can drop the VAT column on every run, reliably, forever. An eval is how you find out whether the work is right, and it's what lets you change your rules without fear.

Takes about 15 minutes to read, 30 to tryBefore this Writing your skill file

What an eval is

An eval is a test for work that has no single correct answer. It has three parts:

  • Test cases: inputs you've chosen on purpose, including the awkward ones.
  • The thing you're testing: your skill file and your script, as they stand today.
  • A grader: something that decides whether each output passed.

Anthropic's own prompt evaluations course teaches the same three parts, then splits on the last one: who grades. A person, a piece of code or another model.

For our purposes there are two families. Human evals, where a person reads the output against a written rubric, are slow and expensive and still the gold standard, because a person catches the thing you never thought to check. Machine evals, where code or a model grades it, are fast and repeatable and run on every change, but you have to decide in advance what "right" means.

You need both. Human evals tell you what to measure, and machine evals measure it for you from then on.

A human eval

Take the BD analyst from the skill file guide, the one writing prospect research memos. The skill file says lead with the decision, cite every factual claim and keep the executive summary to 3 sentences.

A human eval for that is a rubric and a stack of outputs. The rubric has one row per rule, worded so two people would grade it the same way:

#CriterionPass when
1Decision firstThe first sentence is a recommendation, with no background before it
2CitationsEvery factual claim has (Source: file, p.N)
3Citations hold upSpot-check 3 citations: the page says what the memo says it says
4Summary lengthThe executive summary is 3 sentences or fewer
5Leadership flagA leadership change in the last 18 months is flagged, or there wasn't one
6Client vocabularyIndustry terms match the client's own words
7Would I send itWould you put your name on this as it is?

Number 7 catches everything the first six missed. When it fails while 1 to 6 pass, you've found a rule that isn't in your skill file yet, and finding those is the point of the exercise.

Be strict about how you grade:

  • Grade 20 outputs. Three tells you nothing, 20 is enough to see a pattern.
  • Grade blind. Hide which version produced which output, or you'll mark your own improvements generously.
  • Use two graders working separately, then compare. Where two careful people disagree, the rubric's wording is unclear, so fix it before you grade anything else.
  • Write each failure down word for word: the actual sentence and what was wrong with it. Those notes are what you use to write the next version of your skill file.

Keep a log, one entry per run, in the folder next to the skill file:

2026-07-14 | skill.md v4 | 20 memos | graders: DM, RK
Score: 17/20 pass on all criteria
Failures:
  - 3 memos led with company background instead of the recommendation (crit 1)
  - 1 memo cited a page number that didn't contain the claim (crit 3)
  - 2 memos used "vessel" where the client says "rig" (crit 6)
Disagreement between graders: 2 of 140 judgements (both on crit 7)
Action: rule 1 rewritten to "First sentence must contain the word
        'recommend' or 'do not recommend'." Re-run next week.

That log is worth more than the score. It shows how your rules got tighter over time, and why.

A machine eval

A machine eval is a script that grades the output of your script. It comes in two kinds.

Graded by code, when the answer can be checked

For pulling data out of documents, sorting things into categories, formatting or anything else with a factually correct answer, you don't need judgement. You need a comparison. So you build a golden set: a handful of inputs where you've written down the right answer by hand.

Here's one we built for an invoice script: six invoices, an expected.csv with the right answer for each and a check.py that compares them. Running python3 evals/check.py prints:

GOLDEN SET
  PASS  001-clean.txt
  PASS  002-missing-po.txt
  PASS  003-no-vat-line.txt
  PASS  004-multiline-address.txt
  FAIL  005-duplicate-date.txt
        date: expected '2026-04-21' but got '2026-05-21'
  PASS  006-rounding-mismatch.txt

RULE CHECKS
  PASS  columns match skill.md rule 1 (order and names)
  PASS  currency codes are all in the allowed set
  FAIL  net + vat == gross for every row
        006-rounding-mismatch.txt: 1099.99 + 220.00 != 1320.00
  PASS  no field invented where the source was silent

DETERMINISM
  PASS  two consecutive runs produced the same content hash

9 passed, 2 failed

Both failures are real, and they fail in different ways.

005-duplicate-date has two lines labelled Date:, an invoice date and a payment due date. The script takes the last one and the right answer is the first. That's a bug in the script and a gap in the skill file, which never said which date wins, so the fix goes in both.

The arithmetic check catches something else. 006-rounding-mismatch doesn't add up because the invoice itself is wrong: the script copied it faithfully. That failure should stay on screen until a person has looked at the document. An eval that flags bad source data is doing the job of the senior person who used to notice.

The golden set cases aren't random. 002-missing-po is there because a rule says a missing field becomes an empty cell. 005-duplicate-date is there because a real invoice had two date lines and nobody had decided which one counts. Every case is a bug that happened or a rule that turned out to be unclear, and the set grows one incident at a time.

The rule checks don't need a right answer at all. They're things that must hold for any input: the columns are the ones the skill file lists, currencies come from a known list, net plus VAT equals gross and nothing appears in the output that wasn't in the source. They're quick to write and each one catches a whole family of mistakes, so start here if you're starting anywhere.

Graded by a model, when the answer needs judgement

Some things can't be checked in code. Is the tone right for a regulator? Does the summary actually summarise? Is the memo hedging when it should be direct? For those you use a second model as the grader, often called an LLM judge. The judge is a prompt, and a good one is narrow:

You are grading a prospect research memo against one criterion only.

Criterion: the first sentence states a recommendation, a clear position
on whether to pursue the prospect. Background, company description or
scene-setting is a fail.

<memo>
{output}
</memo>

Answer with exactly one word: PASS, FAIL or UNKNOWN.
Answer UNKNOWN if the memo is empty, cut off or not a memo.

Four things make a judge you can trust:

  • One criterion per judge. Anthropic's guidance for agent evals is to grade each part of the rubric with its own judge. A judge asked to weigh seven things at once gives you a number that means nothing.
  • Pass or fail. "Is this a 6 or a 7" can't be answered the same way twice. PASS or FAIL can, and it's what you act on anyway.
  • A way out. The UNKNOWN option stops the judge inventing a verdict on input it can't read.
  • A different model. Anthropic recommends grading with a different model from the one that wrote the output, because models favour their own writing.

Then calibrate it before you rely on it. A judge is a measuring instrument, and one you haven't checked gives you confident numbers that are wrong.

Calibrating is simple and hardly anyone does it. Grade 20 outputs yourself by hand first, then run the judge on the same 20 and compare. Look at the two kinds of disagreement separately, the ones it passed that you failed and the ones it failed that you passed, because they usually have different causes and an overall "85% agreement" hides both. Rewrite the judge prompt against those specific cases and repeat. People who do this for a living report getting a narrow pass-or-fail judge above 90% agreement in a handful of rounds. After that it can grade the next 2,000 outputs while you sleep.

Judges have three known biases to plan around. They reward long answers over short correct ones. When comparing two answers side by side they favour whichever came first, so shuffle the order. And they prefer text written by their own model family. A rubric line saying "do not prefer longer answers" helps with the first one but doesn't fix it.

How people actually do this

Look at the output before you build anything. Take 20 real outputs, read them and write down every failure in plain words. Hamel Husain, who builds evals for clients, puts this reading at 60 to 80% of the time on a real project. The graders are the easy part. Knowing what to grade is the hard part.

Then sort the failures into two piles. Each one that keeps coming back is either a missing rule, which goes in the skill file, or a check you should have had, which goes in the eval. Every incident lands somewhere, so nothing depends on someone remembering.

Start with 10 to 20 cases. Anthropic's advice for writing skills is to create at least 3 evals before you write long instructions, and to measure how the model does without your skill file first, so you can tell whether your rules helped.

Go for volume over polish. Anthropic's own eval principles say more cases with slightly rougher automatic grading beat a few perfect ones graded by hand. Fifty rough automatic checks beat five perfect manual ones.

Run the evals on every change: every skill file edit, every script change, every model upgrade. That's what pays for the whole exercise, because it tells you when a change that fixed one thing broke another. Without it you're editing rules and hoping.

And keep the log: date, version, sample size, score, failures and what you changed.

Why it matters more for you than for a developer

A developer who ships a bug ships a fix. You sign your name to the output.

If you're putting a memo in front of a client, a filing in front of a regulator or a recommendation in front of a partner, "the AI seemed good" won't stand up. An eval gives you something that will: here are the criteria, here's the sample, here's the score, here's what failed and what we changed. It's the standard you already apply to a junior's work, written down.

It lets you change the rules. Editing a skill file that works is nerve-racking when you might break something you can't see. With an eval you edit, run it and know within a minute. Fear of breaking things is what keeps these systems stuck at version one.

It catches drift. The model underneath gets upgraded, your documents change format, a case turns up that nobody expected. None of that announces itself, and the eval catches it on the next run.

And it's an asset you keep. Your golden set and your rubric are your professional standards, written down and checkable by a machine. The skill file says what good looks like and the eval proves you got there, and neither one lives in anyone's head any more.

Try it this week, in 30 minutes

  • Take 10 real inputs you've already processed.
  • For each one, write down the right answer by hand: a row in a CSV, or two lines on what a good output must contain. That's your golden set. It's the slow part, and you only do it once.
  • Ask Claude Code to write a check.py like the one above that compares your outputs with your golden set and checks the rules in your skill file.
  • Run it and count the failures.
  • Fix the most common failure, in the skill file rather than the script.
  • Run it again and write the log entry.

You now have rules, proof they run the same way twice and proof they give the right answer. That's a system you can hand to somebody else.
